# win-cap

Windows向けの小さな範囲録画アプリ。ScreenToGifの範囲選択と録画を参考に、音声なしのMP4保存に絞った初版です。

v0.1.1では開始時の保存先指定をなくし、小範囲の録画エラーを修正しました。タイトルバーのバージョンで修正版を確認できます。

## ダウンロード

GitHubリポジトリの「Releases」から`win-cap-<バージョン>-windows-x64.zip`をダウンロードし、展開して`win-cap.exe`を起動してください。インストールやRustの導入は不要です。変更内容は[CHANGELOG.md](CHANGELOG.md)に記載しています。

同じリリースの`.zip.sha256`とZIPを同じフォルダーに置くと、PowerShellでダウンロードしたZIPのSHA-256を照合できます（以下はv0.1.1の例）。

```powershell
$expected = (Get-Content win-cap-0.1.1-windows-x64.zip.sha256).Split(' ')[0]
$actual = (Get-FileHash win-cap-0.1.1-windows-x64.zip -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actual -ne $expected) { throw 'ZIPのSHA-256が一致しません。再ダウンロードしてください。' }
```

## 使い方

1. `win-cap.exe`を起動し、「範囲を選択」を押します。
2. 画面をドラッグして録画範囲を選びます。Escでキャンセルできます。
3. 30/60fpsとカーソルの有無を選び、「録画開始」で録画します。開始時に保存先の指定はありません。
4. 操作画面が最小化されたら録画します。`Ctrl + Shift + F10`で停止します。
5. 停止後に新しいMP4の保存先を選びます。保存完了の通知に保存先が表示されます。

保存先の選択をキャンセルすると録画を残し、ボタンが「録画を保存」に変わります。保存先のエラーも同じボタンから再試行できます。保存を完了するまで次の録画は開始しません。

`Ctrl + Shift + F9`は開始/停止の切り替えです。他のアプリが同じショートカットを登録している場合、起動時にエラーを表示します。最小化された操作画面を戻して「録画停止」を押すこともできます。録画中にアプリを閉じた場合は停止後に保存先を選びます。保存せず終了した場合も一時録画を残し、その場所を表示します。

## 初版の範囲

- Windows 10 **2004以降** / Windows 11、x64。Windowsの画面取得とH.264エンコードが利用できる環境が必要です。
- 1つのモニター内の任意範囲。複数のモニターにまたがるドラッグは、開始したモニターの端で切ります。
- MP4 / H.264、音声なし、30/60fpsを上限とする更新ベースの録画。
- エンコーダーが処理しきれないフレームは省略し、完了時に省略数を表示します。
- 選択範囲は48 × 48px以上。H.264の制約に合わせ、奇数の幅・高さは右端・下端を1px短くします。16/32px四方は実機で圧縮に失敗したため、選択時に拒否します。
- 操作画面はWindowsのキャプチャー除外機能で録画から除外します。
- Windows標準のキャプチャー枠はOSの既定の動作に従います。範囲を移動する枠、プレビュー、一時停止、編集、音声、GIF、AV1/HEVC出力は未実装です。

録画中はWindowsの一時フォルダーに、専用の一意なMP4を書き込みます。停止後に選んだ保存先へコピーし、コピーの完了を確認してから一時録画を削除します。別のドライブへも保存できます。既存ファイルは上書きしません。

録画エラー時は原因と一時ファイルの場所を表示します。途中のMP4は再生できない場合があります。保存のキャンセルやコピー失敗では完成した一時録画を保持します。

## 軽さのための構成

RustとWindowsのネイティブUIを使用し、WebViewや別途FFmpegの導入を必要としない構成です。

```
Windows Graphics Capture
  → Direct3D 11で指定範囲をGPU上で切り出し
  → 最大2枚の待機キュー
  → MediaStreamSource / MediaTranscoder
  → MP4 / H.264
```

画面取得・切り出し処理ではCPUへ画素を読み戻さず、切り出したGPUサーフェスをWindowsの動画処理へ渡します。キューが満杯になった場合は新しいフレームを省略します。エンコード中の画像は再利用して上書きせず、別のテクスチャーとして保持します。静止画面でも終了時刻のサンプルを渡し、停止までの時間を残します。

幅または高さが256px未満の範囲では、最初からWindows標準のCPU圧縮を使います。小さい範囲に対応できないハードウェアエンコーダーがあるためです。範囲選択後の画面にもCPU圧縮であることを表示し、選択したサイズを維持します。256 × 256px以上では`HardwareAccelerationEnabled`を有効にしますが、Windowsが実際に選ぶエンコーダーはGPU・ドライバー・環境に依存します。ハードウェア圧縮の利用を保証したり、利用状況を判定して表示したりする機能はありません。取得したモニター全体のGPUフレームから範囲を切り出すため、小さい範囲でも画面取得自体はモニター全体です。

UI技術の新旧より、画像のコピー量、圧縮方法、プレビューや編集用の画像保持が負荷を左右します。ScreenToGifなどの既存アプリより軽いかどうかは未測定です。

参照: [Microsoftの録画構成](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture-video)、[Windows Capture](https://github.com/NiiightmareXD/windows-capture)。

## Windowsでビルド

[Rust](https://www.rust-lang.org/tools/install)のMSVCツールチェーンと、Visual Studio Build Toolsの「C++によるデスクトップ開発」およびWindows SDKを導入してください。

```powershell
cargo build --release --locked --target x86_64-pc-windows-msvc
```

成果物は `target/x86_64-pc-windows-msvc/release/win-cap.exe`。CRTを静的リンクする設定です。実行時にRustの導入は不要です。

```powershell
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo fmt --check
```

GitHub Actionsでは同じ検査・ビルドを実行し、バージョン付きZIPとSHA-256をActionsの成果物として14日間保存します。

## GitHubリリースの設計と手順

通常のブランチpush・Pull Request・手動実行では、検査・ビルドと成果物の保存までを行います。`vMAJOR.MINOR.PATCH`タグのpushでは、同じWindowsビルドの成功後にGitHub Releaseを自動公開します。手動実行でタグを選んでも公開しません。

バージョンの正本は`Cargo.toml`です。タグは`v`を付けた同じバージョンでなければビルド前に停止します。現在は安定版形式のみを受け付け、プレリリース用の接尾辞やビルドメタデータは受け付けません。`CHANGELOG.md`の同じバージョンの節をリリース本文として使用し、節がない場合や空の場合も停止します。

配布するZIPには`win-cap.exe`、README、CHANGELOG、MITライセンス、依存ライブラリーのライセンス表記を含めます。リリース用ジョブは同じ実行の成果物を取得してSHA-256を照合し、ZIPと`.zip.sha256`を添付します。[GitHub CLIの`--verify-tag`](https://cli.github.com/manual/gh_release_create)で既存のタグを必須とし、書き込み権限はそのジョブだけに付与します。認証にはGitHub Actionsが発行する`GITHUB_TOKEN`を使います。

初回はGitHubにリポジトリを作成し、そのURLを`origin`に設定して`main`をpushしてください。リポジトリでGitHub Actionsが有効であり、組織のポリシーがリリース用ジョブの`contents: write`を許可することが必要です。

リリース時は次の手順で進めます。

1. `Cargo.toml`のバージョンと`Cargo.lock`の自分のパッケージのバージョンを更新し、`CHANGELOG.md`に対応する節を追記します。初回v0.1.1では更新不要です。
2. 本文末尾の実機確認を行い、結果に応じてCHANGELOGの既知の制約を更新します。通常のCIではGPUによる録画テストや操作画面の確認は行いません。
3. 変更をコミットして`main`をpushし、Actionsの成功を確認します。
4. 同じコミットにタグを付け、タグだけをpushします（v0.1.1の例）。

   ```sh
   git tag -a v0.1.1 -m "Release v0.1.1"
   git push origin v0.1.1
   ```

5. Actionsの`release`ジョブとReleasesの添付ファイルを確認します。タグのpushが公開操作になるため、実機確認とリリース本文の確認はタグ作成前に終えてください。

検査・ビルド・チェックサムの検証に失敗した場合は公開しません。既存のリリースを上書きせず、同じタグの再公開はエラーとして停止します。作成・添付の途中で失敗し、未完成の下書きが残った場合は、その下書きを確認・削除してから失敗したジョブを再実行してください。公開済みの版に修正が必要な場合は、新しいバージョンで公開します。

パッケージ処理はPython 3.11以上の標準ライブラリーだけで実行できます。ローカルではWindowsでビルドしてから、次を実行してください。既に同じ出力がある場合は上書きせず停止するため、該当するZIP・SHA-256・`dist/release-notes.md`を削除してから再実行します。

```sh
python .github/scripts/release.py check --tag v0.1.1
python .github/scripts/release.py package
```

Rustツールチェーンは既存のCIと同じ`stable`を使用します。同じタグを別の時点でビルドした際のバイナリー完全一致は保証しません。公式ActionsはコミットSHAで固定しています。

## 検証状況と実機での完了条件

初版のWindows実行で、104 × 84pxの範囲がエンコード時に`0xC00D6D60`となる不具合を確認しました。合成画像を使った同じ処理でも再現し、640 × 480pxでは成功したため、小範囲の圧縮経路を修正しました。修正後は48 × 48、64 × 64、104 × 84、256 × 256、640 × 480pxでサイズを変えずにMP4を生成し、1秒の静止映像の尺も確認しました。

Windows GPUで合成画像のMP4生成・サイズ・静止画面の動画時間を確認するテストを用意しています。画面内容を取得しないテストで、Windowsの通常のCIでは自動実行しません。

```powershell
cargo test --locked --test encoding -- --ignored --nocapture
```

負荷比較、長時間録画、複数モニターの実機確認は未実施です。

操作画面でも、単色のテスト用ウィンドウ内の104 × 84pxを選択し、開始時に保存ダイアログが出ないこと、停止後の保存ダイアログ、キャンセル後の「録画を保存」、再保存の完了通知まで確認しました。画質と実再生の確認は別途必要です。

Windows実機では次の条件を確認してください。

| 確認 | 期待する結果 |
| --- | --- |
| 録画開始 | 保存先を指定せず録画が始まる |
| 通常の範囲を10秒録画して停止 | 停止後に保存先を選び、指定範囲のMP4が再生でき、尺がほぼ10秒 |
| 保存をキャンセルして再試行 | 「録画を保存」から保存し直せる |
| 静止画面を10秒録画 | 静止中も停止までの時間が動画に残る |
| 100%/150%表示、左側・上側のモニター | 選択範囲と実際の映像が一致する |
| カーソルを含む/含まない | 設定に従って映像に入る |
| 60fps、大きい範囲、5分以上 | メモリーが時間に比例して増え続けない |
| 開始直後の停止、録画中にアプリを閉じる | UIが固まらず、保存完了または理由付きエラー |
| モニター切断、解像度変更、保存先への書き込み失敗 | 成功として扱わず、理由と一時ファイルの場所を表示 |
| 同じ保存名への再録画 | 既存の動画を上書きしない |

負荷比較は同じPC・範囲・fps・映像内容・録画時間で、CPU、GPUのVideo Encode、メモリー、出力サイズと再生の滑らかさを比べます。タスクマネージャーのVideo Encodeはハードウェア圧縮の確認の手掛かりになります。
